  - 클로드-인-크롬으로 테스트 계정(testing@church.com)을 팀원으로
    전환해 소팀장(B-2) 권한을 신청하고, 다시 관리자로 전환해 승인

    permissionRequests 문서의 status는 여전히 pending으로 남아있었음
  - 원인: approvePermissionRequest가 updateUser → 신청 상태 갱신
    순서로 서로 다른 두 번의 await 호출(update)을 순차 실행하고
    있었는데, 두 번째 쓰기의 firestore.rules 보안 규칙(isAdmin())이
    이미 첫 번째 쓰기가 반영된 "현재" 서버 상태를 기준으로 평가됨.
    승인자 본인이 신청자이기도 한 경우(테스트 계정으로 역할을
    스스로 전환하며 요청/승인을 한 계정으로 함) 첫 번째 쓰기로 이미
    role이 small_leader로 바뀌어 버려서 두 번째 쓰기 시점엔
    isAdmin()이 false가 되어 거부당함. 실사용에서는 관리자/목사님
    계정에 "권한 신청" 섹션 자체가 보이지 않아 발생할 수 없는
    조합이지만, 두 쓰기가 원자적으로 묶여 있지 않다는 것 자체는

    있어서, flutter_plugin_android_lifecycle이 요구하는 API 36과

    1) file_picker 13.x는 완전히 새 정적 API로 개편됨

       새 API에 맞게 수정(`FilePicker.pickFile(...)` +
       `await file.readAsBytes()`)
    2) file_picker 13.x가 요구하는 windows_file_picker ^2.0.0(→
       win32 ^6.3.0)가 당시 쓰던 share_plus(<13.0.0, win32 ^5.5.3)와

       Kotlin 컴파일이 "ShareSuccessManager 등 참조를 찾을 수 없음"
       오류로 실패. 원인을 추적한 결과, 이 프로젝트의 AGP가 9.0.1로

       충돌하는 것이었음 — share_plus/file_picker(의 실제 구현체인
       android_file_picker) 모두 자기 build.gradle 안에 "AGP
       메이저 버전이 9 이상이면 자체적으로 kotlin-android 플러그인을
       적용하지 않고 AGP의 Built-in Kotlin에 맡긴다"는 조건부 코드를
       최신 버전에서만 갖고 있었음. 반면 예전에 시도했던 file_picker

       `false`(Flutter 템플릿 기본값)에서 `true`로 변경해야 이 최신

■ 안드로이드 release 서명 키스토어 생성 및 서명 설정 적용
  - 배경: "앱 배포 방식을 APK를 활용해서 진행해 보려고 하는데 지금
    방식에서 제한되는 기능이 있어?"라는 질문에, release 빌드가

  - `keytool -genkeypair`로 android/app/upload-keystore.jks(별칭
    upload, RSA 2048, 유효기간 2054-02-12까지)를 생성. PKCS12
    포맷은 storePassword와 keyPassword가 서로 달라도 실제로는
    keyPassword가 무시되고 storePassword로 덮어써진다는 keytool
    경고를 확인해, android/key.properties에 두 값을 동일하게 설정
  - android/app/build.gradle.kts에 key.properties를 읽어 release
    signingConfig을 구성하는 코드를 추가. key.properties가 없는
    환경(CI 없이 처음 체크아웃한 경우 등)에서는 디버그 키로
    자동 폴백해 빌드 자체는 항상 가능하도록 함. key.properties와
    upload-keystore.jks는 android/.gitignore에 이미 걸려 있어
    git에는 커밋하지 않음

■ 심방 신청 데이터 Firestore 보안 규칙 강화
  - 배경: "중팀장 역할로 접속했을 때 심방 신청 내용에 본인 외에
    자기 중팀원이 신청한 내역이 뜨네. 이 내용은 무조건 목사님
    역할만 볼 수 있게 해줘"라는 신고. 클라이언트 코드(visit_screen.
    dart)는 이미 user.isPastor가 아니면 무조건 streamUserVisits
    (본인 uid로 where 필터링)만 쓰도록 되어 있고, 실제로 로그인
    상태로 재현해봐도 본인 신청 내역만 보여 클라이언트 단에서는
    문제를 재현하지 못함
  - 원인 추적 중 firestore.rules의 visits 컬렉션 read 규칙이
    `allow read: if isSignedIn()`으로, "로그인한 사용자는 대부분
    컬렉션을 폭넓게 읽을 수 있다"는 이 프로젝트의 전역 설계 원칙을
    그대로 따르고 있었음을 발견 — 즉 클라이언트 UI가 본인 것만
    보여주는 건 순전히 클라이언트 쿼리의 where 필터 덕분이고,
    서버 규칙상으로는 로그인한 아무나 Firestore에 직접(또는
    streamAllVisits류 쿼리로) 접근하면 전체 회원의 심방 사유·
    연락처를 읽을 수 있는 상태였음. 심방 정보는 다른 컬렉션과
    달리 민감한 개인정보라 이 전역 원칙의 예외로 둬야 할 항목
  - firestore.rules에 isPastor() 헬퍼 함수를 추가하고, visits의
    allow read를 `isOwner(resource.data.userId) || isPastor()`로,
    allow update도 isSmallLeader() → isPastor()로 좁힘(실제 앱에서
    심방 상태 변경은 목사님 화면에서만 가능하므로 UI 동작과 일치
    시킴). `firebase deploy --only firestore:rules`로 배포 완료
  - 클로드-인-크롬으로 배포 후 재검증: 테스트 계정을 중팀장으로
    전환해 본인 심방 신청 내역은 그대로 보임(isOwner 통과)을 확인,
    목사님으로 전환해 전체 심방 신청 목록이 여전히 정상적으로
    보임(isPastor 통과)을 확인. 두 번째 계정이 없어 "타인 소유
    문서를 직접 읽으면 거부되는지"까지는 실측하지 못했으나, 규칙
    문법·필드명(userId) 모두 다른 컬렉션의 기존 isOwner 패턴과
    동일하게 작성해 신뢰도 높음
